    7. Block protocols¶

    Depth: L2 · Reading time: ~10 min · Last verified: 2026-11-01 Prerequisites: What storage does · Inside an SSD · Performance and economics metrics

    TL;DR¶

    • A block protocol is a command set riding a transport (plus fabric services for discovery and access control). SCSI rode parallel cables, Fibre Channel (FC) and TCP/IP (iSCSI). NVMe replaced it, and NVMe over Fabrics (NVMe-oF) carries NVMe over FC, RDMA or TCP.
    • NVMe's advantage is its queue model, not raw bandwidth. Up to 65,535 I/O queues of up to 64K entries, one or more per core, driven by doorbell registers with no shared lock.
    • NVMe/TCP is the enterprise default trajectory. It runs on any Ethernet NIC and every major OS and array, and adds roughly 20–35 µs, small next to a flash read.
    • NVMe over RoCE (RDMA on Ethernet) wins AI back-ends. GPU servers already carry 400G RDMA NICs, and copy-free data movement keeps GPUs fed.
    • Fibre Channel is not dying. FC sales grew in 2025 and 128G switches launched. Most FC estates will move to NVMe/FC on the same hardware.

    Why this matters for Everpure strategy¶

    FlashArray is a block array, so its revenue rides on whichever wire the customer's servers use. Transport transitions are when customers re-platform and incumbents lose share. Two current examples: VMware-exit projects, where Everpure's May 2025 Nutanix partnership attaches FlashArray to AHV hosts over NVMe/TCP1, and AI clusters, where storage must sit on the RDMA fabric the GPUs already use.

    Protocol support is now table stakes. The strategic questions are subtler. Which transport will buyers standardize on for a decade? Who controls discovery and automation? Does end-to-end NVMe (Everpure's DirectFlash, see Chapter 26) become a measurable edge once the front end is NVMe too?

    Core concepts¶

    What a block protocol does¶

    A block protocol lets a server (the initiator, or host) read and write numbered fixed-size blocks on a remote device (the target). It asks for "block 1,000,000, 256 blocks long" and knows nothing about files, which are the job of the file system above (see Chapter 1). Every block protocol has three layers:

    1. Command set. READ, WRITE, FLUSH and error reporting. SCSI uses a Command Descriptor Block (CDB) addressed to a LUN. NVMe uses a 64-byte Submission Queue Entry (SQE) addressed to a namespace.
    2. Transport. How commands, data and status cross the wire: parallel SCSI, FC, TCP/IP, PCIe or RDMA.
    3. Fabric services. Discovery, naming, access control and multipathing: FC zoning, iSCSI qualified names (IQNs), NVMe Qualified Names (NQNs) and discovery controllers.

    The command set and the transport evolve on different clocks.

    SCSI: a command set that outlived its cable¶

    SCSI was standardized in 1986 for disks on a ribbon cable2. Its command model is rich (sense codes, persistent reservations that clusters use for fencing) and was designed when a disk access took about 5 ms. A 20 µs software stack was then 0.4% of the I/O; against an 80 µs flash read it is 25% (worked example).

    The bigger problem is queuing. SCSI-era stacks present roughly one queue per device per path, and cores contend for its lock. SATA's AHCI is the extreme: one queue, 32 commands deep. Sustained IOPS ≈ outstanding commands ÷ latency, so 32 commands at 100 µs caps a device at 32 ÷ 0.0001 s = 320,000 IOPS, however fast the NAND behind it. Linux later retrofitted multi-queue layers (blk-mq, scsi-mq) and modern FC and SAS HBAs expose several hardware queues, but per-LUN queue depths and the heavier SCSI command path still cap concurrency well below NVMe's.

    Fibre Channel and iSCSI: two ways to network SCSI¶

    Fibre Channel (FC-PH, 19943) built a dedicated, lossless network for SCSI. Lossless is the defining property. Each link uses buffer-to-buffer credits: a sender transmits only as many frames as the receiver has advertised buffers for, so congestion never drops frames. Semiconductor bridge: this is PCIe's flow-control credit scheme stretched across a building. FC adds a name server and zoning (an access-control list on the switch) and maps SCSI onto frames through FCP. The result is deterministic, offloaded in HBAs and run by the storage team. It also needs its own switches (in practice Broadcom's Brocade or Cisco MDS), HBAs and skills.

    iSCSI (RFC 3720, April 20044) put the same SCSI commands into TCP/IP, so any Ethernet network and any server NIC could build a SAN. It made SANs affordable for the mid-market, at the cost of host CPU for TCP and Ethernet's lossy, shared nature.

    NVMe: a protocol designed around queues¶

    NVMe 1.0 (March 20115) was written for flash on PCIe and organizes the interface around paired rings in host memory:

    • A submission queue (SQ) holds 64-byte commands. A completion queue (CQ) holds 16-byte completions.
    • The host may create up to 65,535 I/O queue pairs, each up to 64K entries deep6. The driver typically gives each CPU core its own pair, so no core waits on another's lock.
    • The command set is small and fixed-format, so the controller parses commands in hardware without walking variable-length CDBs.

    Figure 7.2 — NVMe replaces one lock-protected queue with a private queue pair per core; parallelism comes from the interface, not from heroic per-command speed.

    Little's law again: 64 cores each keeping 32 commands in flight gives 2,048 outstanding. At 100 µs that is about 20 million IOPS of addressable concurrency, far beyond any single SSD. The interface stops being the bottleneck.

    Semiconductor bridge: NVMe is a DMA engine with descriptor rings. The host writes a descriptor (the SQE) into a ring in DRAM, then performs one memory-mapped write to a doorbell register in the SSD's PCIe BAR to announce the new tail pointer. The SSD, a PCIe bus master, fetches the descriptor by DMA, moves the data by DMA to or from the host buffers the descriptor points to, writes a completion entry into the CQ (with a phase bit so the host can tell new entries from stale ones), and raises an MSI-X interrupt. The host consumes completions and rings a second doorbell to free CQ slots. PCIe is NVMe's native transport: the protocol assumes the device can reach host memory directly.

    sequenceDiagram
    participant D as Host driver on core k
    participant R as SQ k and CQ k in host DRAM
    participant C as NVMe SSD controller
    D->>R: write 64 B READ command into SQ k
    D->>C: MMIO write to SQ k tail doorbell
    C->>R: DMA fetch the command
    C->>R: DMA write data into host buffer
    C->>R: write 16 B completion into CQ k
    C->>D: MSI-X interrupt to core k
    D->>C: MMIO write to CQ k head doorbell

    Figure 7.3 — Local NVMe over PCIe: one doorbell write starts the I/O and the device does the rest by DMA, which is why the host-side cost is a few microseconds.

    NVMe-oF: stretching the rings across a network¶

    A remote SSD cannot DMA descriptors out of host DRAM, so NVMe-oF (1.0 in June 2016, with RDMA and FC bindings7) sends them. The 64-byte SQE travels in a command capsule, optionally with small-write data inside, and the completion returns in a response capsule. Each NVMe queue pair maps onto one transport connection (an RDMA queue pair, a TCP connection or an FC-NVMe connection within an association), preserving per-core parallelism end to end. Multipathing uses ANA (Asymmetric Namespace Access), NVMe's equivalent of SCSI ALUA (see Chapter 14).

    The transports differ mainly in how bulk data moves:

    • RDMA (RoCEv2 on Ethernet, or InfiniBand). The capsule carries the address and key of a registered host buffer; the target RDMA-WRITEs read data into it, or RDMA-READs write data out of it. No host CPU copies a byte, and the adder is about 5–15 µs over local NVMe8. The price is RDMA NICs and, for RoCE, carefully tuned Ethernet (see Chapter 10).
    • TCP. Capsules and data travel as PDUs on a TCP stream: reads return as C2HData PDUs (the last one may carry a success flag so the target can skip the response capsule), and writes larger than the in-capsule limit wait for an R2T, as in iSCSI, then send H2CData PDUs. The kernel copies payloads and runs TCP; early Linux tests showed 20–35 µs added9. Under heavy load the gap widens: one 2018 vendor test measured 183 µs average for TCP versus 107 µs for RoCE, although single-I/O latency was within a few microseconds10.
    • FC (FC-NVMe, standardized by T11 in 201711). Capsules ride FC frames on the same HBAs, switches, zoning and lossless credits as SCSI-FC, with data movement offloaded to the HBA.

    Why NVMe/TCP is the enterprise default trajectory¶

    NVMe/TCP was ratified in November 2018 (TP 8000)14, reached upstream Linux in 5.015 and VMware in vSphere 7 Update 3 in late 202116. Four reasons it is winning new Ethernet SANs:

    1. No special hardware. It runs on existing NICs and routes like any TCP traffic; RoCE needs RDMA NICs and carefully engineered switches.
    2. The penalty is small where it counts. A 20–35 µs adder over a 100–200 µs array round trip is real but rarely decisive for databases or VMs. A 2021 SNIA talk reported realistic performance similar to RoCEv217.
    3. CPU cost is falling. More cores and NIC/DPU offloads shrink the copy overhead.
    4. It replaces iSCSI without retraining. Same network, same team, better queue model.

    The gaps are operational: discovery at scale (Dell's SmartFabric Storage Software is a centralized discovery controller for this18), authentication and TLS, and tail latency on congested networks.

    Why RoCE wins AI back-ends¶

    In an AI cluster the economics flip. GPU servers already carry several 400G RDMA NICs, so RDMA is free, and at hundreds of gigabits per server CPU copies would burn host cores. GPUDirect Storage needs an RDMA-capable path to land data directly in GPU memory (see Chapter 11). Disaggregated back-ends such as VAST's use NVMe over RDMA internally (see Chapter 16). NVIDIA claims its Spectrum-X adaptive routing gives almost 50% more storage read bandwidth than plain RoCEv2, in its own tests19.

    Why Fibre Channel persists¶

    FC's survival is organizational as much as technical: a separate lossless fabric with a small blast radius, change control owned by the storage team, and mature diagnostics under decades of mission-critical databases. Its NVMe upgrade path is cheap, because NVMe/FC runs on the same 32G-and-later HBAs and switches. Crehan Research reported FC networking sales up 6% in 2025, with 64G about half of shipments20 [VERIFY: search-summary only], and Broadcom launched Gen 8 128G Brocade switches in November 202521.

    Figure 7.7 — Everpure shipped RoCE early and followed on TCP; by 2026 the three vendors are at parity on NVMe/FC and NVMe/TCP (only Everpure offers RoCE on these lines), so differentiation sits in the internal data path and the automation around discovery.

    Everpure shipped RoCE first, a bet on latency-sensitive databases. Its structural argument is that DirectFlash already speaks NVMe from controller to raw NAND, so an NVMe front end removes the last SCSI translation (see Chapter 26). The steelman for competitors is strong. Dell's centralized discovery addresses a real NVMe/TCP pain point at scale, NetApp's unified ONTAP serves FC, NVMe and NAS from one estate, and because FC customers rarely change fabric, the incumbent with the deepest FC relationships often holds the account. Options a strategy team might evaluate, based on public information: owning NVMe/TCP automation in VMware-exit and Nutanix deals, and judging how much AI back-end RoCE demand reaches block arrays rather than file and object (FlashBlade; see Chapter 27).

    History and trajectory¶

    timeline
    title Block protocol lineage
    1986 : SCSI-1 standard for parallel disks
    1994 : Fibre Channel FC-PH, a lossless SAN for SCSI
    2004 : iSCSI RFC 3720 puts SCSI on TCP
    2011 : NVMe 1.0 for PCIe flash
    2016 : NVMe-oF 1.0 with RDMA and FC bindings
    2017 : FC-NVMe standard completed in T11
    2018 : NVMe over TCP ratified as TP 8000
    2021 : NVMe 2.0 library and vSphere NVMe over TCP
    2025 : 128G Gen 8 Fibre Channel switches

    Figure 7.8 — The command set changed once in 25 years (SCSI to NVMe); transports keep multiplying because each buyer segment brings its own fabric.

    A command set is born on a local bus, then re-ridden across every network: SCSI from ribbon cable to FC to TCP, NVMe from PCIe to RDMA and FC to TCP. The June 2021 NVMe 2.0 refactor made each transport its own specification29.

    Signals to watch: NVMe/TCP offload on DPUs (erasing its CPU penalty), better Ethernet RDMA congestion control (making RoCE easier outside AI), FC's move to 128G, and whether hyperscaler-style block services (see Chapter 19) pull enterprise buyers toward NVMe/TCP-only designs.

    Conversation playbook¶

    Questions for a PM

    1. "In new FlashArray deals, what share of hosts attach by NVMe/TCP versus FC versus iSCSI, and how has that shifted in two years?" Strong: a measured mix from telemetry, by segment, and whether NVMe/TCP is displacing iSCSI or FC.
    2. "When a VMware customer moves to Nutanix or another hypervisor, does the storage protocol change, and who decides?" Strong: names the decision-maker and whether NVMe/TCP automation shortens the cycle.
    3. "Where do we lose block deals on protocol grounds?" Strong: specific cases (a missing automation integration, an FC estate locked to a competitor), not "we support everything."

    Questions for an engineer

    1. "What is the latency delta between NVMe/TCP and NVMe/RoCE on FlashArray at queue depth 1 and at saturation?" Strong: both numbers, host CPU per IOPS, and where tail latency diverges.
    2. "How do ANA paths and controller failover behave on NVMe-oF versus ALUA on SCSI?" Strong: path-state transitions and failover time.
    3. "Does the array's internal NVMe path change how many queue pairs per host you can serve?" Strong: concrete queue and connection limits per port, and behaviour with thousands of Kubernetes hosts.

    Don't say this:

    • "NVMe-oF is faster because the wire is faster." The wire is the same; the gain is the queue model and no SCSI translation.
    • "Fibre Channel is dead." Sales grew in 2025 and 128G is shipping. Say "shrinking share, durable base."
    • "NVMe/TCP is too slow for real work." It adds tens of microseconds, not milliseconds.
    • "RoCE is the same as InfiniBand." RoCE shares RDMA semantics but runs on Ethernet and depends on congestion management.
    • "iSCSI and NVMe/TCP are interchangeable." Same network, different command set and queue model.

    Going deeper (optional, L3 pointers)¶

    • NVM Express base and transport specifications (2.x library): capsule formats, SGLs, ANA.
    • Linux nvme-tcp, nvme-rdma and nvmet drivers, and blk-mq queue-to-CPU mapping.
    • iSCSI RFC 7143 and T11 FC-NVMe-2 (transport error recovery).
    • Kernel-bypass storage stacks (SPDK) and NVMe/TCP offload on DPUs.

    Key terms¶

    • Initiator / target — host issuing block commands; device executing them.
    • LUN / namespace — the SCSI and NVMe names for an addressable block volume.
    • SQ / CQ — NVMe's command and completion rings.
    • Doorbell — device register announcing new queue entries.
    • Capsule — NVMe-oF command or response message.
    • ANA — Asymmetric Namespace Access, NVMe's multipath path-state mechanism.
    • R2T — Ready to Transfer, a target's invitation for the host to send write data.
    • See the glossary for the rest.
