    36. How hyperscalers build AI storage¶

    Depth: L2 · Reading time: ~10 min · Last verified: 2026-11-01 Prerequisites: Parallel file systems · Object storage architecture · Metadata · Training storage · Purity and DirectFlash

    TL;DR¶

    • Hyperscalers build the file system and buy the parts. Google (Colossus), Meta (Tectonic) and AWS (S3) run home-grown software that turns a datacenter of commodity drives into one pool. They buy no arrays for their own workloads.
    • The designs are close cousins. A smart client library, metadata on a scalable database (Bigtable for Colossus, ZippyDB for Tectonic) and simple data servers, with no controller in the data path.
    • AI pushed them from disk toward flash. Built on HDDs with a little flash, these systems met GPU clusters that need far more bandwidth per terabyte. Meta's GenAI clusters run on flash-optimized Tectonic; Google, AWS and Azure sell zonal, GPU-adjacent tiers.
    • Where hyperscalers do buy, they buy components and IP, not systems. Meta and a second top-five hyperscaler licensed Everpure's DirectFlash design while buying their own NAND. Cloud services do resell partners (DDN Lustre at Google, VAST listings) for tenants.
    • It is the same logic as TPU, Trainium and Nitro. Build where volume amortizes engineering and the part differentiates. Buy where a merchant supplier has more scale. Vendors win at the seams.

    Why this matters for Everpure strategy¶

    The top hyperscalers are the largest buyers of storage media on earth, yet almost closed to storage-system vendors. For Everpure (NYSE: P, formerly PSTG) that matters three ways. Its hyperscaler revenue exists only because Pure Storage found a seam: a licence for flash-management software and module design, with the customer buying its own NAND12. Hyperscaler designs set the reference architecture that neoclouds and enterprises copy. And whether hyperscalers keep cold data on HDD or move it to QLC is the largest swing factor in flash-versus-disk demand (Chapter 48).

    Which layers hyperscalers build, which they buy, and why the boundary moves defines the addressable surface for licensing deals. Chapter 29 covers the deal financials; this chapter covers the engineering behind the boundary.

    Core concepts¶

    The common pattern: one disaggregated file system per datacenter¶

    An enterprise array puts intelligence in a controller between host and drives (Chapter 14). Hyperscale file systems remove that box:

    • A client library in every application encodes data, finds where it lives and streams it directly to or from storage servers.
    • A metadata service runs as a sharded application on a scalable database; file names and block maps are just rows.
    • Thin data servers expose local disks over the network, while background workers repair and rebalance.

    Semiconductor bridge. Moving the RAID logic into the client is like moving the memory controller onto the CPU die. It removes a hop and a box, but only works if you control every application and its libraries. Hyperscalers do; enterprise vendors don't, so they sell controllers and standard protocols.

    Google Colossus¶

    Colossus succeeded GFS as Google's cluster-level file system and sits under Cloud Storage, Firestore, YouTube, Drive and Gmail3. Its control plane is a pool of Curators, which store file-system metadata in Bigtable. That change let Colossus scale metadata more than 100× beyond the largest GFS clusters. Data flows directly between the client library and D file servers, which are network-attached disks. Custodians handle rebuilds and disk balancing3.

    flowchart LR
    subgraph HOST["Application host"]
        APP["App: Spanner, Cloud Storage, training job"]
        CL["Colossus client library: encoding, software RAID"]
        APP --> CL
    end
    CL -- "control: open, create, locate" --> CU["Curators: scalable metadata service"]
    CU <--> BT[("Bigtable: file metadata")]
    CL == "data: direct" ==> DH["D file servers on HDD"]
    CL == "data: direct" ==> DS["D file servers on SSD"]
    L4["L4: ML-driven SSD cache index"] -.-> CL
    CUS["Custodians: rebuild, rebalance"] -.-> DH
    CUS -.-> DS

    Figure 36.1 — Colossus keeps metadata in a database and data on simple disk servers; the client library, not a controller, owns the data path.

    Two Colossus file systems each hold more than 10 exabytes; the largest regularly exceed 50 TB/s of reads and 25 TB/s of writes, and the busiest cluster serves over 600 million IOPS4. At ~250 MB/s per HDD, 50 TB/s is the streaming bandwidth of 200,000 drives.

    The economics come from mixing media: Google buys just enough flash to lift I/O density to what applications need, and just enough disk for capacity3. A tier called L4 decides which data earns SSD, running a read cache and a writeback policy that simulates options such as "SSD for one hour" per file category. The same simulations drive SSD purchasing4. Semiconductor bridge: L4 is a last-level cache with a learned replacement policy, sized by simulating hit rates before buying silicon.

    For AI, Rapid Bucket (GA April 2026) is a zonal Cloud Storage bucket on Colossus; Google claims more than 15 TB/s, 20 million requests per second and sub-millisecond latency in one bucket. Rapid Cache (formerly Anywhere Cache) adds up to 2.5 TB/s of read cache in front of existing buckets5. For POSIX users Google sells Managed Lustre, built with DDN's EXAScaler, now claimed at up to 10 TB/s per instance, about 10× its 2025 launch figure56. All three figures are Google's own.

    Meta Tectonic¶

    Tectonic, Meta's exabyte-scale multitenant file system (USENIX FAST '217), runs one cluster per datacenter. It replaced separate systems for photo and video blobs (Haystack and f4) and many HDFS clusters for the data warehouse78. Warehouse clusters fell 10×8.

    flowchart TB
    subgraph TEN["Tenants"]
        BLOB["Blob storage"]
        DWH["Data warehouse"]
        AIT["AI training via FUSE"]
    end
    TEN --> CLB["Client library: per-tenant tuning, EC or replication"]
    CLB --> MS
    subgraph MS["Metadata Store, hash-partitioned layers"]
        NL["Name layer"] --> FL["File layer"] --> BL["Block layer"]
    end
    MS --> ZDB[("ZippyDB: sharded key-value store")]
    CLB == "data: direct" ==> CS["Chunk Store: flat chunk storage on storage nodes"]
    BG["Background services: repair, rebalance"] -.-> CS
    TG["TrafficGroups: shared quotas across tenants"] -.-> CLB

    Figure 36.2 — Tectonic splits metadata into layers on a shared key-value store and gives each tenant its own client-side tuning over a common chunk pool.

    Two ideas matter. Disaggregated metadata: names, files and blocks are separate layers, each hash-partitioned into a key-value store, so a hot directory does not overload the servers holding block maps78. Multitenancy without per-tenant clusters: tenants share a few dozen traffic groups, so the blob store's peak no longer strands disks the warehouse could use8, while tenant-specific tuning such as erasure-code width lives in the client library. It is the hyperscale version of the consolidation argument (Chapter 19).

    AI changed the media. Meta's two 24,576-GPU GenAI clusters (2024) use a home-grown FUSE client on a flash-optimized Tectonic, plus a parallel NFS deployment co-developed with Hammerspace, both on YV3 Sierra Point servers with high-capacity E1.S SSDs9. A worked number shows why. A 405B-parameter checkpoint with optimizer state is ~405e9 × 16 bytes ≈ 6.5 TB. Writing it in 60 seconds needs ~108 GB/s. That is ~430 HDDs at ~250 MB/s streaming flat out, before erasure-coding overhead, or ~22 NVMe SSDs at ~5 GB/s.

    Meta's July 2026 "AI storage blueprint" adds regional, flash-backed BLOB storage colocated with GPUs, a client SDK embedding Tectonic's block client to skip proxies, hedged reads against tail latency, and GPU-host memory and local flash as L1/L2 caches10: a cache hierarchy around one source of truth (Chapter 31).

    In March 2025 Meta argued for QLC flash as a middle tier, because HDD bandwidth per terabyte falls as drives grow. Meta places QLC at workloads that still need about 10 MB/s per TB, between HDD and TLC; some batch workloads at 15–20 MB/s/TB sit on TLC today11. The arithmetic: a ~250 MB/s drive gives 12.5 MB/s/TB at 20 TB at best, but only 8.3 MB/s/TB at 30 TB. Under mixed access real HDD clusters deliver less: a 2025 Meta conference deck put HDD-cluster supply at 5–7 MB/s/TB12. Meta named Pure Storage's DirectFlash Module and standard QLC SSDs from other vendors1113.

    AWS: object store at the centre, file and cache at the edge¶

    AWS builds a layered stack around S3, which AWS said at re:Invent 2025 holds more than 500 trillion objects and hundreds of exabytes14. A peak near 1 PB/s is cited from an earlier AWS talk15 [VERIFY: S3 ~1 PB/s peak bandwidth, secondary source only].

    flowchart TB
    subgraph EC2["EC2 GPU and Trainium instances"]
        MPT["Mountpoint for S3 and PyTorch connector"]
        LCL["Lustre client with EFA and GPUDirect Storage"]
    end
    MPT --> S3X["S3 Express One Zone: same-AZ directory buckets"]
    MPT --> S3S["S3 Standard: regional data lake"]
    LCL --> FSX["FSx for Lustre: POSIX training and checkpoint tier"]
    FSX <-- "lazy load and export" --> S3S
    S3S --- TBL["S3 Tables: managed Iceberg"]
    S3S --- VEC["S3 Vectors: vector indexes"]

    Figure 36.3 — AWS keeps S3 as the system of record and adds zonal object, parallel file and client-side layers to bring bandwidth next to the GPUs.

    • S3 Express One Zone (November 2023) puts directory buckets in the compute's Availability Zone for single-digit-millisecond access. AWS claimed 10× faster access than S3 Standard at launch16, then cut storage prices 31% and GET prices 85% in April 202517.
    • FSx for Lustre, a managed parallel file system linked to S3, has since November 2024 supported EFA and GPUDirect Storage at up to 1,200 Gbps (150 GB/s) per client, 12× the earlier 100 Gbps TCP limit18.
    • Mountpoint for S3 (GA August 2023), an open-source client, maps file reads to S3 GETs at up to 100 Gb/s per instance19.
    • S3 Tables (Iceberg, December 2024) and S3 Vectors (GA December 2025, up to 2 billion vectors per index) pull analytics and RAG data into the object layer2021 (Chapter 33).

    AWS did not invent a new file system for AI. It runs open-source Lustre as a service and keeps proprietary effort where scale pays: the object store, the EFA network and Nitro offload cards.

    Azure: Blob at exabyte scale plus managed Lustre¶

    Microsoft centres on Blob, whose "scaled accounts" let OpenAI run exabyte-scale datasets across regions22. For POSIX, Azure Managed Lustre's AMLFS 20 SKU (preview, November 2025) reaches 25 PiB and 512 GB/s in one namespace, which is 20 MB/s per TiB: a bandwidth-light, capacity-heavy tier, with one extra metadata server per 5 PiB23. Azure was the first hyperscale service submitted to MLPerf Storage, at 642 GiB/s checkpoint write in v3.024 (Chapter 37). Azure also offers VAST through its Native ISV Service25.

    DeepSeek 3FS: the open hyperscale design¶

    DeepSeek open-sourced its Fire-Flyer File System (3FS) in February 202526. Its design follows the same pattern: stateless metadata services on a transactional key-value store (FoundationDB), chain replication (CRAQ) for strong consistency, and storage nodes shared by all clients. A 180-node cluster, each node with 2×200 Gb/s InfiniBand and sixteen NVMe SSDs, reached ~6.6 TiB/s aggregate reads27. Per node: 6.6 TiB/s ÷ 180 ≈ 37.5 GiB/s, against a line rate of 400 Gb/s ≈ 46.6 GiB/s, or ~80% of the NIC. Built for AI rather than photo archives, it is all-flash. It shows an AI lab can build hyperscaler-class storage and give it away, which pressures proprietary software pricing.

    Build versus buy, and the custom-silicon parallel¶

    Buyer Builds Buys Why
    Top hyperscalers (Google, Meta, AWS, Microsoft) File system, metadata, erasure coding, caching, client libraries; servers to OCP-style specs HDDs, NAND/SSDs, NICs; selective IP licences (DirectFlash); partner software inside some cloud services Exabyte scale amortizes large teams; control of the whole stack; media is a commodity where suppliers have scale
    AI labs with own clusters (DeepSeek, Meta FAIR-type) Lean parallel FS (3FS) or a tuned hyperscaler FS Servers, SSDs, InfiniBand Workload is narrow and known; talent concentrated
    Neoclouds (CoreWeave, Nebius, Lambda) Object layer and GPU-side caches (e.g., CoreWeave LOTA)28 Dedicated file systems from VAST, WEKA, DDN, Everpure28 Time to market; customer demand for certified, known systems; small storage teams (Chapter 35)
    Large enterprises Almost nothing below the data platform Arrays and SDS (Everpure, NetApp, Dell, VAST) or cloud services No scale to amortize a storage team; need support, SLAs, features

    Table 36.1 — The build boundary falls as scale rises: hyperscalers build everything except media, neoclouds build only the GPU-side glue, and enterprises buy systems.

    The logic mirrors silicon. Google ran the TPU for about a year before announcing it in May 201629. AWS bought Annapurna Labs in 2015 to build Nitro, then Graviton and Trainium (announced December 2020)30. The design is proprietary; the wafers come from a foundry. In storage, the file system is the chip design and NAND and HDDs are foundry capacity bought on the merchant market. A DirectFlash licence is like licensing a SerDes or CPU core: IP that speeds up an in-house design without ceding control to a system vendor.

    Table 36.2 — Vendors enter hyperscalers either through internal infrastructure as IP or components, or through cloud services as managed partners; only the first touches the exabytes.

    The steelman against Everpure is that hyperscalers can build it. NVMe Flexible Data Placement, driven by Meta and Google, lets standard SSDs take placement hints and removes much of the write amplification DirectFlash targets (Chapter 26). Meta runs standard QLC SSDs alongside DFMs11. The counter-argument is revealed preference: when Meta wanted raw-flash control at scale, it licensed it, and a second top-five hyperscaler followed in August 2026, with revenue expected from FY20282. Options a strategy team might evaluate, based on public information: which other hyperscaler file systems face the same HDD-to-flash pressure, and whether the licence can extend to software above the FTL.

    Figure 36.4 — The disk-era file systems of 2003–2021 were rebuilt around flash and GPU locality in 2023–2026.

    Two signals point forward. Storage is moving next to the GPUs: zonal buckets, regional BLOB stacks and host-memory caches trade durability domain for latency and bandwidth. Flash is advancing into capacity tiers: in August 2025 Pure Storage expected to ship 1–2 exabytes of DirectFlash to Meta by the end of FY2632. HDDs still dominate hyperscale exabytes, and bears argue disk keeps a large TCO edge (Chapter 48); the debate is how fast flash takes share.

    Conversation playbook¶

    Questions for a PM

    1. "Which hyperscaler file systems besides Tectonic hit the same HDD bandwidth-per-TB wall?" Strong: names workloads (warm blob, AI data lakes) and how the licence fits each file system, not just the Meta story.
    2. "What do we deliver to a hyperscaler that FDP plus a standard QLC SSD doesn't?" Strong: numbers on density per rack, power, write amplification and the software the customer would otherwise maintain.
    3. "Could the licence model sell to tier-2 clouds or neoclouds that lack a Tectonic?" Strong: the licence assumes the buyer has its own file system; others need a full system such as FlashBlade//EXA.

    Questions for an engineer

    1. "Where does DirectFlash sit relative to the hyperscaler's file system?" Strong: at the media and flash-management layer under the storage servers, with the file system still owning placement, erasure coding and metadata (public sources don't detail the integration).
    2. "How do hyperscalers stop GPU stalls from tail latency?" Strong: hedged reads, client-side concurrency control, host-memory and local-NVMe caches, and zonal placement, as in Meta's 2026 blueprint.
    3. "What would it take for Colossus's L4 tier to move bulk data from HDD to QLC?" Strong: cost per unit of bandwidth versus cost per TB; once HDD must be over-provisioned for bandwidth, flash wins.

    Don't say this:

    • "Hyperscalers buy storage arrays." Internally they buy media and occasional IP.
    • "Meta replaced its disks with Pure." Meta adds QLC as a middle tier alongside HDDs and also uses standard QLC SSDs.
    • "We compete with Colossus or Tectonic." They are internal; we compete with services built on them, such as Rapid Bucket.
    • "3FS proves storage software is worthless." A lab with a narrow workload can build its own; enterprises still pay for support and features.

    Going deeper (optional, L3 pointers)¶

    • Tectonic FAST '21 paper: layered metadata and consistency semantics7.
    • CacheSack, cited in the 2025 Colossus post: the admission policy behind L44.
    • 3FS design notes: CRAQ and the USRBIO zero-copy client API27.

    Key terms¶

    • Colossus / Curator / D file server — Google's cluster file system, its metadata servers (on Bigtable) and its simple disk servers.
    • L4 cache — Colossus's ML-driven SSD caching and placement tier.
    • Tectonic / ZippyDB / Chunk Store — Meta's multitenant file system, the key-value store holding its metadata, and its flat data layer.
    • S3 Express One Zone / Rapid Bucket — AWS and Google zonal, low-latency object tiers built for AI.
    • Smart client — a client library that does placement and encoding itself, so no controller sits in the data path.
    • Hedged read — a duplicate request sent to a second replica to cut tail latency.
