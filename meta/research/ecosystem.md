### 1.7 NVIDIA Dynamo, NIXL and KVBM
- Dynamo is NVIDIA's open-source (Apache 2.0) distributed inference-serving framework, written in Rust and Python. It is engine-agnostic (TensorRT-LLM, vLLM, SGLang), and NVIDIA positions it as the successor to Triton Inference Server. — Source: NVIDIA Developer, "NVIDIA Dynamo", n.d., https://developer.nvidia.com/dynamo (retrieved 2026-11-01)
- Dynamo was announced at GTC in March 2025. [VERIFY: GTC 2025 announcement date (believed 2025-03-18); not retrieved directly this session]
- **NIXL** (NVIDIA Inference Xfer Library) is an open-source library for point-to-point data movement (KV cache) across GPU memory, CPU memory and storage. It is used by Dynamo, TensorRT-LLM, vLLM, SGLang and Ray. — Source: NVIDIA Developer Blog, NIXL post, n.d., https://developer.nvidia.com/blog/?p=113426 (retrieved 2026-11-01) [VERIFY: title/date]
- **KVBM (KV Block Manager)** tiers KV blocks across G1 (GPU HBM), G2 (host DRAM), G3 (local SSD) and G4 (remote/object storage). Disk I/O goes through NIXL via POSIX, using GDS where available. G4 is treated as an opaque blob store reached through NIXL. Default NIXL backends are UCX and POSIX. — Source: NVIDIA Docs, "KVBM design", Dynamo docs v1.3.0, n.d., https://docs.nvidia.com/dynamo/v1.3.0/design-docs/component-design/kvbm-design.md (retrieved 2026-11-01)
- In recent Dynamo versions, disk offload filtering is on by default to extend SSD life: blocks move from CPU to disk only if accessed at least twice. — Source: NVIDIA Dynamo docs, "KVBM Guide / KV cache offloading", n.d., https://docs.dynamo.nvidia.com/dynamo/user-guides/kv-cache-offloading (retrieved 2026-11-01) [VERIFY: version-dependent]
- Dynamo docs exist for v1.0.0, v1.0.1, v1.1.1 and v1.3.0, so Dynamo reached 1.x during 2026. A third-party cookbook still installed v0.9.1 in March 2026. — Source: NVIDIA Docs (versioned KVBM pages above); Vultr Docs, "NVIDIA Dynamo overview", 2026-03, https://docs.vultr.com/inference-cookbook/cuda/dynamo/dynamo-overview (retrieved 2026-11-01) [VERIFY: Dynamo 1.0 GA date]

## 2. KV cache offload ecosystem

### 2.1 Open source
- **LMCache** is an open-source KV cache layer. It pulls KV caches out of GPU memory in vLLM and SGLang and shares them across engines and queries, supporting both prefix-reuse offload and prefill/decode disaggregation. It was presented at MLSys 2026. — Source: arXiv, "LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference" (2510.09665), 2025-10, https://arxiv.org/pdf/2510.09665 (retrieved 2026-11-01); MLSys 2026 oral listing, https://mlsys.org/virtual/2026/oral/3646 (retrieved 2026-11-01)
- **vLLM** documents tiered KV offloading across host memory, storage and remote peers. It leaves peer selection to an orchestration layer such as llm-d. — Source: vLLM Blog, "Tiered KV Cache Offloading in vLLM", 2026-09-10, https://vllm.ai/blog/2026-09-10-tiered-kv-offloading (retrieved 2026-11-01)
- **llm-d** supports KV offload two ways: natively through vLLM's OffloadingConnector (CPU RAM plus a shared-filesystem "llm-d FS" backend), or through third-party connectors such as LMCache. Hierarchical GPU→CPU→storage offload in the native path is under active development. — Source: llm-d docs, "KV-Cache Offloading", n.d., https://llm-d.ai/docs/architecture/advanced/kv-management/kv-offloader (retrieved 2026-11-01); llm-d docs, "Offloading Prefix Cache to Shared Storage", n.d., https://llm-d.ai/docs/dev/guides/tiered-prefix-cache/storage (retrieved 2026-11-01)
- llm-d's governance (Red Hat-led, CNCF status) was not confirmed in this session. [VERIFY: llm-d founding members / foundation home]

## 3. MLPerf Storage

### 3.1 How it works
- MLPerf Storage emulates accelerators in software with "sleep" compute time, so no real GPUs are needed. The score is the largest number of simulated accelerators a storage system can keep fed while each stays above a required accelerator-utilization (AU) threshold. — Source: HPCwire, "The New MLPerf Storage Benchmark Runs Without ML Accelerators", 2024-10-03, https://www.hpcwire.com/2024/10/03/the-new-mlperf-storage-benchmark-runs-without-ml-accelerators/ (retrieved 2026-11-01)
- For the training workloads, a run passes only if AU is 90% or above. — Source: Quobyte Blog, "MLPerf Storage Benchmark 2025 Preliminary Results", 2025, https://www.quobyte.com/blog/mlperf-storage-benchmark-2025-preliminary-results/ (retrieved 2026-11-01) [VERIFY: per-workload AU (UNet3D vs ResNet50/CosmoFlow may differ, e.g., 70% for CosmoFlow) against MLCommons rules]
- v3.0 KV cache metric: tokens can be generated only as fast as storage delivers the KV caches they depend on. MLCommons' David Kanter described the score as the number of conversations a system supports. — Source: MLCommons, "Benchmark MLPerf Storage", n.d., https://mlcommons.org/benchmarks/storage/ (retrieved 2026-11-01); TechArena, "MLPerf Storage v3.0 Expands Into AI Inference", 2026-09, https://techarena.ai/content/mlperf-storage-v3-0-expands-into-ai-inference (retrieved 2026-11-01)
